## 1. 现状盘点（已核实，非推测）

### 1.1 已有能力

| 层 | 具备 |
|---|---|
| 界面 | 项目网格（封面 + 名称 + `N 张 · 厂商`）· 详情视图（返回 / 名称 / 模块数 / 每项卡片）· 空态 · 错误态 |
| HTTP | `GET /pixmart/api/projects?limit=N`（默认 50）· `GET /pixmart/api/projects/<id>` · `GET /pixmart/file/<projectId>/<name>`（`private, max-age=31536000, immutable`） |
| 工具 | `pixmart_projects`：`list` / `get` / `export` / `delete`（须 `confirm:true`）/ `usage` |
| 存储 | `projects/<id>/project.json` + `projects/<id>/images/<sha8>-<slug>.<ext>`，**无索引文件，列表靠目录扫描** |

### 1.2 核心问题：磁盘上已有的数据，一半被丢掉了

| 数据 | `project.json` | HTTP 透出 | UI 显示 |
|---|---|---|---|
| 项目 `name` / `createdAt` / `provider` / `model` | ✅ | ✅ | 名称 ✅ · **时间 ❌** |
| 每项 `prompt`（提示词） | ✅ | **❌** | ❌ |
| 每项 `model` / `ms` / `createdAt` | ✅ | **❌** | ❌ |
| 每项 `degraded`（降级链路）/ `error`（失败原因） | ✅ | **❌** | ❌ |
| 每项 `apiMode` | ✅ | ✅ | **❌** |
| 每项 `size` / `status` / `label` | ✅ | ✅ | ✅ |

**后果**：用户**看不到"当时用的什么提示词"**。而本插件的核心资产正是**提示词与产物的对应关系**——图留下了，怎么做出它的却丢了。失败项也看不出**为什么**失败。

### 1.3 操作能力：后端有一半，前端一点没接

| 能力 | 工具层 | HTTP | UI |
|---|---|---|---|
| 列出 / 查看 | ✅ | ✅ | ✅ |
| 导出项目 | ✅ | ❌ | ❌ |
| 删除项目 | ✅ | ❌ | ❌ |
| 复制提示词 / 同参数重新生成 | — | — | ❌ |
| 搜索 / 排序 / 分页 | 部分（`limit`） | 部分 | ❌ |

### 1.4 已知边界

- **`project.json` 是唯一真相**，作品库只是它的视图。任何改名/删除都必须同时处理文件与视图，且要与 `pixmart_projects` 工具保持一致。
- 宿主是**零运行时依赖**（勿引入图像库，见 §4 决定②）。

## 2. 方案（四批，按真实痛点排序）

### 第 1 批：把已丢弃的信息显示出来 ★ 最高性价比

**做什么**
- 项目卡片补**创建时间**
- 详情项补：**提示词**（可一键复制）· **模型** · **耗时** · **时间** · **降级标记** · **失败原因**
- 失败项必须能看出失败原因（现状等于空白）

**改动面**：API 多透 6 个字段（**纯读，无副作用**）+ 前端渲染。
**风险**：极低（不触碰任何写路径）。
**验收**：详情里能看到并复制提示词；失败项显示 `error` 原文；`degraded` 非空时可见标记。

**为什么排第一**：数据已在磁盘，当前状态是"付了钱、留了证据、却不给看"。做完才从"图片浏览器"变成"生产记录"。

### 第 2 批：操作能力（需新增 HTTP 路由）

- **删除项目**（破坏性，必须二次确认，实现方式见 §4 决定①）
- **导出项目**（拷到指定目录 / 生成清单）
- **复制提示词** · **同参数重新生成**（复用 `pixmart_generate` / `pixmart_edit`；**必须显式提示将产生费用**，见 §4 决定③）

**改动面**：新增 3 条路由 + UI。
**风险**：中——首次给作品库写入/删除能力。
**验收**：删除需二次确认且可恢复（若采用软删）；重新生成前出现费用提示。

> **施工后的语义修订（2026-10-06，见 §4 决定⑤）**：导出不再是"默认落到数据目录的
> `exports/`"那种**顺带产物**，而是**唯一的对外写出口**——目标目录取设置里的
> 「作品库导出路径」，没配就 400 并提示去配置。相应地，生图侧的「产物保存路径」
> 自动复制被**取消**：生成只写数据目录。

### 第 3 批：规模化（项目一多才痛）

- **搜索**：按项目名 / 模块名
- **排序**：时间正倒序
- **懒加载**：网格 `loading="lazy"` + `decoding="async"`，且**只加载封面**

**改动面**：主要前端。
**风险**：低。
**验收**：50+ 项目时首屏不卡；搜索与排序生效。

### 第 4 批：体验

- 大图查看器（点开看原图、左右切换）
- 前后对比（同一模块不同版本）
- 多选批量删除 / 导出
- 项目重命名

## 4. 审核决定项（**未定前不要开工**）

### 决定① 删除：真删还是软删？

- **建议：软删**（移到 `projects/.trash/`，可恢复），并提供一个"清空回收站"入口。
- 理由：项目目录是唯一真相，`pixmart_projects` 工具与文件路由都依赖它；**误删后没有回收站就找不回来**。
- 代价：多一个回收站概念与清理入口。

> **已定（2026-10-05）：软删 + 回收站。** 删除移入 `projects/.trash/` 可恢复；另提供"清空回收站"入口。
> 理由：项目目录是唯一真相，工具与文件路由都依赖它；误删后没有回收站就找不回来。

### 决定② 缩略图：做还是不做？

- **建议：这一版不做**。宿主是零运行时依赖，没有图像库；靠 shell 调 Python/Pillow 做缩略图脆弱且丑。
- 替代：**CSS 限尺寸 + 懒加载**，接受"网格仍加载原图"的带宽代价。
- 引入图像库会破坏"零依赖"这条设计基石，**得不偿失**。

> **已定（2026-10-05）：不做缩略图。** 采用 CSS 限尺寸 + 懒加载，接受网格加载原图的带宽代价；
> 不引入图像库，保持零运行时依赖这条设计基石。

### 决定③ 重新生成的费用提示到什么程度？

- **建议**：按钮直接标 **「重新生成（计费）」**，点击后要求确认。
- 立场：**不隐藏费用**是本插件一贯做法（见 guidance 里的计费顺序规定）。

> **已定（2026-10-05）：按钮标注「重新生成（计费）」+ 点击后二次确认。**
> 这是**唯一一条不经 Agent 就直接花钱的路径**，护栏单独设计（见 §7）。

### 决定④ 是否改动 `pixmart_projects` 工具的返回形状？

- **建议：不动**。第 1 批只**新增**字段（向后兼容），且优先只改 HTTP 层，避免影响已验证的 Agent 路径。

> **已定（2026-10-05）：工具层不动。** 只在 HTTP 层新增字段（向后兼容），保持已验证的 Agent 路径不变。
> **（2026-10-06 补充）**：后来只为语义一致性改了一个字段名——`pixmart_providers` 回传的
> `outputDir` 改成 `exportDir`（并说明"生成时不复制"）；`pixmart_projects` 的形状与
> `export` action 的落点**仍然未动**。

### 决定⑤ 生成时要不要自动把副本写到用户指定的目录？

- **已定（2026-10-06）：不要。取消「产物保存路径」（`outputDir`）的自动复制。**
- 理由：**生成不该有未经请求的副作用**。用户没说要副本，插件却在他磁盘上多写一份，
  还得替这份副本回答"谁清理""原件改了怎么办"这类问题；而它换来的便利（Agent 有个
  稳定路径可以 `present`）本可以由用户在需要时**显式导出**一次得到。
- 做法：图片只落插件数据目录（作品库浏览）；设置页那一栏改成「**作品库导出路径**」
  （`exportDir`），**只有**在作品库点「导出」时才复制到 `<该路径>/<项目 id>/`。
  没配置就 400 `no_export_dir`，界面给出"先去设置里填"的可读提示，**不静默失败**。
- 迁移：旧的 `outputDir` 有值而 `exportDir` 缺键时，把旧值搬过来并记 warning
  （用户已填的路径不能凭空消失）；此后 `outputDir` 不再被读、不再有任何行为。
- 会话内嵌附件（DSH 用来在对话卡片显示图片的那条落点）**不动**：它是显示机制，
  不是用户的保存路径。
- 不做清理：插件**不删除**用户磁盘上已经存在的那份旧副本（例如 `E:\Programs\agent\out` 里
  已有的文件），只在文档里说明这份历史副本与插件此后无关。

## 6. 施工切分与「重新生成」的护栏

### 6.1 切分

| 批次 | 内容 | 状态 |
|---|---|---|
| **A** | 第 1 批（信息可见性）+ 第 2 批的**无费用部分**（软删 + 回收站、导出、复制提示词） | 施工中 |
| **B** | **重新生成**（唯一直接花钱的按钮） | 待议，护栏见 §6.2 |
| **C** | 第 3 批（搜索 / 排序 / 懒加载）+ 第 4 批（查看器 / 对比 / 多选 / 重命名） | 待排 |

### 6.2 为什么把「重新生成」单列

它是**唯一一条不经 Agent 就直接产生费用的路径**。在此之前每一笔花费都经过模型，
而模型受 guidance 约束（先跑免费工具、批量前必须报价）。加这个按钮等于开了**一条绕过模型
的新计费通道**，所以护栏必须单独设计：

1. **按钮文案含「计费」**，点击后必须二次确认（已定，见决定③）
2. **服务端二次校验**：请求体必须带显式 `confirm: true`，缺失即拒绝 —— 防误触与脚本误调
3. **必须写入账本**：与 `generate` / `edit` 共用同一本账，并标记来源（如 `source: 'ui'`），
   否则账本又会多出一块"看不见的花费"——这正是刚修完的漏记 bug 的同类风险
4. **并发限制**：同一项目同时只允许一次重新生成，防连点重复计费
5. **不得自动重试**：失败就是失败，**不得为"修好它"再花一次钱**

> 未落实第 2–5 条之前，不要实现这个按钮。
