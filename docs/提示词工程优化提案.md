## P0：便宜、可测、直接补掉"自证不了"的洞

### P0-1 给提示词**打版本号 + 哈希**，写进项目/用量记录
- **问题**：`project.json` / `usage.jsonl` 里**没有提示词标识**。改了模块文本之后，**无法判断某张旧图是哪个版本出的**，也无法回滚到一个"当时更好"的版本。这和待办 T1（图生图无法自证参考图）是同一类病。
- **改法**：`buildPrompt()` 返回里加 `promptHash`（对最终提示词 + 负向 + 模块 id 取稳定哈希）与 `promptVersion`（模块表版本号，人工递增）；项目记录与 `usage.jsonl` 都写上。作品库详情可显示"提示词版本 + 哈希前 8 位"。
- **成本**：小（半天内，纯宿主 + 断言）。**风险**：几乎为零（只加字段）。
- **怎么验证**：同模块两次调用 → 哈希相同；改一个字符 → 哈希变化（**可证伪**）。

### P0-2 加一个**提示词 linter**（当测试跑）
- **问题**：24 个模块 × 条件分支（有/无参考图、有/无产品、有/无 var）目前**只有"能出图"这一层证据**；没有一条断言能防止"拼装出语法残缺或自相矛盾的提示词"。
- **改法**：对**每个模块 × 每种入参组合**（有/无参考图 × 有/无 product）跑一遍 `buildPrompt()` 并断言：
  1. **无未替换的 `{xxx}`**（这条现在有没有断言？值得核）；
  2. 每个 fragment 经过 F2 之后**仍非空**（哪怕被删也要有替代句）；
  3. **句子级不重复**（跨片段重复的整句 = 复读）；
  4. 负向词条数有上限（例如 ≤ 12 个 "no X"），且不与正向片段直接冲突；
  5. 总长度在预算内（不同模型容忍度不同，先按最大公约数定一个阈值）。
- **成本**：小—中（主要是把"入参组合"枚举出来）。**风险**：低。
- **怎么验证**：故意改坏一个模块（把 subject 全写成 "of the reference image"）→ linter 必须红。

### P0-3 **F2 从"删整句"改成"改写指代"**
- **问题**（我认为这是当前最实质的隐患）：F2 现在是 `含 reference 的整句 → 删掉`。两个后果：
  - **丢信息**：`main.white-bg.subject` 的 "Preserve the exact silhouette, colors, material sheen **and every printed packaging text of the reference image**" 会被**整句删掉** —— 但"保留轮廓/颜色/材质"在文生图里**仍然想要**，不能因为尾巴提到参考图就整句丢；
  - **可能删空**：某些模块的 subject/scene 若全靠参考图句式，删完就剩零碎句子（P0-2 的第 2 条正是要拦住它）。
- **改法**：把"删句"换成**短语级改写**：`the reference image` → `the product described above`；`identical to the reference image` → `internally consistent`。同时对**确实只在有参考图时才成立**的句子用一个**显式标记**（例如片段写成 `[ref]…[/ref]` 或 `requiresReference` 拆到片段粒度）而不是靠 `\breference\b` 猜。
- **成本**：中（要逐模块过一遍 24 × 5 个片段）。**风险**：中 —— **会改变现有文生图输出**，必须配 A/B 真机对比（每模块 1 张，24 张 ≈ $0 但 ~5 分钟）。
- **怎么验证**：改写前后各出 1 张同模块同尺寸图，人工对比；linter 断"无参考图时 subject/scene 仍非空且不含 reference 字样"。

## P1：结构性改进（收益大，但要动数据契约或界面）

### P1-1 `variables` 升级为**带默认值/说明/示例的对象**
- **问题**：现在 `variables: ['background']` 只是一个名字数组；缺值时替换成**未受控的"中性描述"**（那串到底是什么、谁审过？）。界面上也无法据此生成表单，客户端只能硬编码提示。
- **改法**：
  ```ts
  variables: [{ name:'background', hint:'背景环境，如 木质桌面 / 大理石台面', example:'a warm oak tabletop',
                default:'a clean neutral surface that matches the product category' }]
  ```
  好处：① 默认值**可审、可测**；② 界面能自动生成带提示的输入框；③ 生成卡能显示"这个模块需要哪些信息"。
- **成本**：中（改契约 + 24 个模块的变量表 + 客户端表单 + 断言）。**风险**：低（向后兼容：仍接受字符串数组）。
- **怎么验证**：缺 var → 用 declared default（断言逐字）；给了 var → 逐字替换。

### P1-2 把**最终提示词**暴露到界面（带"保存为覆盖"）
- **问题**：`overrides` 能力已经存在（`build.ts:197`），但用户**看不到拼出来的是什么**，也就无从改。现在只有 Agent 侧 `pixmart_prompt` 能看。
- **改法**：生成卡/设置页加"查看提示词"（含拼装调整说明与负向），并提供"以此为基础编辑并保存为本机覆盖"。
- **成本**：中（客户端为主）。**风险**：低。
- **怎么验证**：保存覆盖 → 下张图的 `promptHash` 变化且提示词文本逐字含覆盖内容；清除覆盖 → 回到默认。

### P1-3 **负向提示按"模型有没有真正的负向通道"分流**
- **问题**：现在负向是一行长文本（"负向提示：No A, no B, …"）。对**没有独立负向参数**的模型（agnes/gpt-image 这类 images-generations），把 "no watermark, no extra text" 混进正向文本，**有时反而会召唤出这些东西**。
- **改法**：声明能力的 `supportsNegative`；支持的走独立参数；不支持的用**正向重写**（`no artifacts` → `clean, artifact-free edges`），并限制条数。
- **成本**：中。**风险**：中（要 A/B，否则只是"我觉得这样更好"）。
- **怎么验证**：抽 3 个模块 × 2 种写法各 1 张，人工盲评；记录在 contract-notes。

## P2：产品层面的增量（要你拍方向）

### P2-1 **品类感知层**（category overlay）
- 现在 24 个模块**与品类无关**（珠宝/食品/服装共用一套场景与光）。改法：加一层"品类 → 场景/光/道具/禁忌"的**可审默认值**（数据，不是代码分支），与模块正交组合。
- 成本：中—大（要有 8–12 个品类的可用默认值，且需要真机抽样）。**风险**：中高（品类判断错会污染提示词）。

### P2-2 **广告模块的文案保真**
- `ad.poster` / `ad.social` 必然要画面里有字。现在靠 `copyStyle` + 变量，但**"渲染指定文案"与"不要自创文字"是一对矛盾指令**，需要明确策略（例如：文案作为 var 逐字给出 + 负向禁止其它文字 + 指定字体/位置）。
- 成本：小—中。**风险**：中（文字渲染本身是模型弱项，要设预期）。

### P2-3 **按厂商/方言的语言与长度策略**
- 现在**所有厂商收同一份英文提示词**。国内几家（通义/火山/腾讯）对中文指令往往更稳；gpt-image 对超长提示更敏感。
- 改法：**声明式**策略表（`dialect → {language, maxChars}`），只影响装配，不重写模块。
- **我的倾向**：**先不做**，等有具体失败样本再上；否则就是凭印象加分支。

## 我不建议做的（anti-scope，供你否掉）

1. **不要把 24 个模块重写成中文**：英文对当前主力模型更稳（`modules.ts:8-11` 的判断是对的），而且一改就要 24 张真机对比。
2. **不要为单个模型加"魔法咒语"**（某些社区提示词技巧）：短期看着好，换模型就崩，且无法解释。
3. **不要盲目加模块数量**：模块是**数据**，加模块几乎零成本，但"哪个模块在什么场景下更好"没人能验证 —— 先把 P0/P1 的可测性补上，再谈扩模块。
4. **不要在提示词里塞参数**（尺寸/张数/质量）：那些该走 API 参数，混进文本会与适配器的参数归一化打架（§27/§35 的教训）。
