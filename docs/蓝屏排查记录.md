# 蓝屏排查记录（2026-10-07）

> 结论先说：**6 次蓝屏是同一个内核 bugcheck，且参数高度一致 —— 这是"某个内核驱动里一条
> 确定的代码路径"在崩，不像随机内存故障**（与用户侧 memtest 通过一致）。
> **DSH 是用户态程序，它自身无法让内核蓝屏**；但它可以是**触发器**：它把某个第三方内核
> 驱动逼到那条路径上。要定位到具体是哪个 `.sys`，下一步必须分析 dump（见 §5）。

## 1. 证据：6 次崩溃的 bugcheck 参数

来源（两条，互相印证）：

```powershell
# ① 事件日志：BugCheck 记录（Event 1001）与"未正常关机"（Kernel-Power 41）
Get-WinEvent -FilterHashtable @{LogName='System'; Id=1001,41} -MaxEvents 12 |
  Select-Object TimeCreated,Id,ProviderName,Message | Format-List

# ② 内存转储文件本体
Get-ChildItem C:\Windows\Minidump | Sort-Object LastWriteTime -Descending
```

| 崩溃时间 | Dump | bugcheck | 参数 1 | 参数 2 |
|---|---|---|---|---|
| 2026-10-07 10:30 | `100726-7296-01.dmp` | `0x1A` | `0x00000000000d8a18` | `0xffffffffc0000005` |
| 2026-10-06 18:09 | `100626-6859-01.dmp` | `0x1A` | `0x00000000000d8a18` | `0xffffffffc0000005` |
| 2026-10-06 17:34 | `100626-6312-01.dmp` | `0x1A` | `0x00000000000d8a18` | `0xffffffffc0000005` |
| 2026-10-06 17:21 | `100626-6796-01.dmp` | `0x1A` | `0x00000000000d8a18` | `0xffffffffc0000005` |
| 2026-10-06 17:14 | `100626-7093-01.dmp` | `0x1A` | `0x00000000000d8a18` | `0xffffffffc0000005` |
| （更早一次） | — | `0x1A` | 同上 | 同上 |

读法：
- `0x1A` = **MEMORY_MANAGEMENT**；参数 2 = `0xC0000005` = **STATUS_ACCESS_VIOLATION**
  （一次非法内存访问）。
- **参数 1 六次完全相同（`0xd8a18`）**，参数 2 也完全相同 —— 这种"每次都一样"是最有价值
  的线索：它说明是**可复现的代码路径**，而不是随机的位翻转（后者 bugcheck 与地址会散乱）。
- 参数 3/4 每次都不同（`0x4013f7` / `0x3f9412` / `0x40343c` / `0x3e8a2f` / `0x142e51` …
  与几个 `0xffff…` 内核指针）：参数 3 落在**低地址区间**（`0x0014xxxx`–`0x0040xxxx`），
  像是**用户态地址**——"内核代码去访问一个已经不在的用户态缓冲区/页面"是设备过滤类驱动的
  典型翻车姿势。

## 2. 旁证：写入中的文件被 NTFS 零填充

本会话观察到 **`lib/` 31 个文件、`dist/client.js` 整份（291346 字节全零）被零填充**，
而**源码零 NUL**。这不是应用层能造出的现象：应用层写坏自己的文件只会写坏内容，
不会"整份变零且大小不变"。它更像**在写入路径上的过滤驱动**（或回写/缓存环节）出错留下的痕迹。

## 3. 这台机器上加载的第三方内核驱动（嫌疑名单）

```powershell
Get-CimInstance Win32_SystemDriver |
  Where-Object { $_.State -eq 'Running' -and $_.PathName } |
  Select-Object Name,DisplayName,PathName | Sort-Object Name
```

与"写文件 + 内存管理"最相关的几家：

| 驱动 | 归属 | 为什么在名单上 |
|---|---|---|
| `hrdevmon.sys`（Huorong Internet Security **Devmon**） | **火绒** | "设备监控"= **I/O 过滤驱动**，就在写入路径上；与 §2 的零填充现象最吻合 |
| `sysdiag.sys`（Huorong Core）、`hrwfpdrv.sys`（WFP） | 火绒 | 核心钩子 + 网络过滤；安全软件是 `0x1A` 的常见来源 |
| `ACE-BOOT.sys`（`C:\Program Files\AntiCheatExpert\`） | **腾讯 ACE 反作弊** | 全局内存/句柄钩子，反作弊驱动历史上 BSOD 记录很多 |
| `gvinput.sys` / `gvinputmf.sys`、`ViGEmBus.sys` | 虚拟手柄/输入 | 内核态输入钩子 |
| `nfwfp.sys`、`adgnetworkwfpdrv.sys` | 第三方网络过滤 | WFP 过滤驱动 |
| `amdfendr.sys` / `amdfendrmgr.sys`（AMD Crash Defender） | AMD | 它专门"接管/掩盖崩溃"，本身也是内核驱动 |
| `amdkmdag.sys`（显卡）、`AMDRyzenMasterDriver.sys` | AMD | 显卡/超频驱动，历史上也会 `0x1A` |

**注意**：列在名单上 ≠ 有罪。要定罪必须看 dump 的调用栈。

## 4. 为什么"其他软件没问题"不能排除这些驱动

过滤驱动崩不崩，取决于**它被调用的频率与并发度**。本会话的工作负载恰好是最苛刻的一类：
**短时间大量小文件写入 + 多进程并发写 + 频繁原子替换（写临时文件再 rename）**
（`lib/` 重建、`dist/` 生成、多个 lane 同时跑、子智能体并行改文件）。
其他软件只是没有把它逼到那条路径上。

## 5. 下一步（决定性的一步：把 dump 交给 WinDbg）

```powershell
winget install Microsoft.WinDbg      # 或从应用商店装 "WinDbg"
windbg -z C:\Windows\Minidump\100726-7296-01.dmp
# 进去后：
!analyze -v
```

`!analyze -v` 会直接给出 **`Probably caused by: <模块>.sys`** 以及调用栈 —— 那就是答案。
把输出贴给我，我可以据此判断是"某个驱动单独有 bug"还是"两个驱动的交互"。

**不想装 WinDbg 也可以做 A/B**（成本更低，结论稍弱）：
1. 暂时**退出/停用火绒的"设备监控"或整体防护**（`hrdevmon` 是可疑度最高的一枚），
   再跑一轮同样的写入负载，看是否还崩；
2. 如果不崩，再开回来确认复现（这一步很重要——否则无法区分"换了变量"与"碰巧"）；
3. 不玩腾讯系游戏的话，`ACE-BOOT` 可以卸载，单独观察一轮。
4. 都无关的话，再查 AMD 显卡驱动（干净重装 DDU + 官方版）。

## 6. 我这边已经做的（降低触发概率，不改功能）

- **减少并发写**：不再让多个子智能体同时改大文件；需要并行时按文件切分并分批落盘。
- **缩小单次写入**：大文件改动拆成多次小编辑，避免"一写就是几百 KB 的新文件"。
- **更频繁提交**：崩溃时最多损失一个提交的量（本会话的 4 个提交都是这么保住的）。
- **崩溃后先扫 NUL**：`lib/`、`dist/` 是产物，可重建；源码若被零填充则 `git checkout --` 还原。

> 一句话：**这不是 DSH 的 bug，但很可能是"DSH 的工作负载 + 某个第三方内核驱动"的组合**。
> 在拿到 `!analyze -v` 的输出之前，我不对具体是哪一枚下结论。
