## 2. 真正的风险场景（都会实际发生）

### R1 **并发被调用次数放大**（最该先修）
`pool()` 是**每次 `pixmart_batch` 调用内部**的池子，**没有进程级闸门**。而我们的工具声明了
`isConcurrencySafe: true` ⇒ **必须假设运行时会并行调用**。于是：
- 2 个 batch 并发（或 batch + `pixmart_edit`）⇒ 对**同一家厂商**的在途请求 = **2 × concurrency**；
- 若每个都显式传 `concurrency: 8` ⇒ **16 个在途**。
对按账号限流的厂商，这直接撞 429（我们虽然会退避重试，但**退避解决的是"重试"，不是"在途数"**）。
**`maxConcurrency` 现在的语义是"每批"，不是"每家厂商全局"** —— 这是最容易被忽略的名实不符。

### R2 大批量 = **多次工具调用**，没有统一任务
`maxBatchItems: 20` ⇒ **100 张 = 5 次以上调用**。后果：
- **没有统一的进度**（用户只能看到"第几批"）；
- **没有统一取消**（要逐个 run 取消）；
- **节奏无法持续控制**（每次调用之间没有节流）；
- 一次调用是**同步长任务**（批量的超时上限已放宽到 15 分钟）——大任务把工具调用挂到超时边缘。

### R3 **崩溃/断连后没有续跑**
`interrupted` 记下了，但**没有"继续这个 run（跳过已成功的项）"的入口**。这台机器**已经蓝屏 7 次**；
一次 100 张的任务跑到 60 张被打断，现在只能**从头再来**（重复付费 + 重复等待）。

### R4 **没有成本闸门**
`$0` 的厂商无所谓，但付费厂商上"100 张 × 4 张/项"能在**一次调用**里花掉一大笔，而我们目前
靠的是**"Agent 自觉先报规模"**这条**纪律**，不是**宿主层面的闸门**。纪律会失手，闸门不会。

### R5 没有**每厂商**差异化限流
agnes / ofox / 国内几家的限流阈值不同；现在只有一个全局 `maxConcurrency`。

### R6 没有**去重/缓存**
同一 `module + vars + size + n` 再要一次，**照价重付**。批量里"同一模块不同颜色"这类场景，
重复项出现的频率比想象中高。

## 3. 方案（分三档，可只批一档）

### ✅ 档 A：**把"在途数"变成宿主保证**（最小、最该先做）
1. **进程级"每厂商"信号量**：`withProviderSlot(providerId, fn)`，config 支持
   `limits.perProvider: { agnes: 2, ofox: 4, default: 2 }`。
   - `pixmart_batch` 的 `concurrency` 语义改成"**本批最多用几个槽**"，**总在途由信号量封顶**；
   - 关键：**batch 与 edit/generate 共用同一个信号量** ⇒ 并行调用也不会放大。
2. **每项超时**：单张请求加 `timeoutMs`（默认建议 180 s）；超时**计入该项失败**并释放槽位
   （现在一个挂住的请求会占着槽不还）。
3. **每厂商独立退避**：同一家的 429 触发后，对该厂商**短暂熔断**（例如 5 s 内不再发新请求），
   而不是让所有在途任务各自傻等。
- **成本**：小（宿主 + 断言）。**风险**：低（只是把既有的"每批"收紧成"每厂商"）。
- **怎么验证（可证伪）**：夹具厂商**计数在途请求**，断言
  ① 单批 `concurrency: 8` 但 `perProvider.agnes = 2` ⇒ **峰值在途 ≤ 2**；
  ② **两个 batch 并发** ⇒ 峰值仍 ≤ 2（这条正是现在的洞）；
  ③ 一个请求挂住 ⇒ 到超时后槽位释放（在途计数回落）。

### ✅ 档 B：**"一次任务 = 一个 run"**（大批量的正解）
1. **run 扩容**：一批可以**超过 `maxBatchItems`**——调用方可以给"要生成的全部项"，
   宿主**自己排队**（内部按 `maxBatchItems` 分片，但对用户是**一个 run**）。
2. **异步任务模型**：项数超过阈值（例如 > 8）时，`pixmart_batch` **立刻返回 runId**
   （"已排入队列"），进度走 `GET /runs/<id>`，作品库侧显示**进度条 + 成功/失败计数**；
   小批量仍走同步（保持现在的体验）。
3. **续跑**：`POST /runs/<id>/resume` —— **跳过已 `ok` 的项**，只补失败的与没跑的。
4. **统一取消**：`POST /runs/<id>/cancel` 已有 ✅（档 B 只是把它接到 UI 上）。
5. **成本闸门（R4）**：调用前给出**预估**（项数 × n）；超过阈值（建议 `items × n > 30`）
   **必须显式带 `confirm: true`**，否则拒绝并返回预估 —— 把"先报规模"从纪律变成**宿主机制**。
- **成本**：中（run 模型 + 路由 + UI 进度 + 断言）。**风险**：中（异步化会改工具的返回契约，
  需要保持"小批量仍然同步"以不破坏现有调用方式）。
- **怎么验证**：① 30 项（> 8）⇒ 立即返回 runId 且状态 `running`；② 轮询到 `done` 后**项数守恒**；
  ③ 中途 `cancel` ⇒ 状态 `cancelled`、在途请求**在 X 秒内归零**（计数断言）；
  ④ `interrupted` 后 `resume` ⇒ **只补未成功项**（计数断言：成功项不重复请求）；⑤ 超阈值无 `confirm` ⇒ 拒绝且**零厂商请求**。

### ☐ 档 C：更远的事（我倾向**先不做**）
- **内容寻址缓存**（R6）：同参数命中缓存直接复用；但"同提示词同参数就该同图吗"是个产品问题
  （用户可能就是想要第 2 版），建议先做**"重复项提示"**而不是自动复用。
- **智能调度**（按厂商成功率动态调并发、跨厂商负载均衡）：收益不确定，先别上。
- **失败率熔断整批**（>50% 失败就停）：值得做，但应放在档 B 之后（有 run 状态才好表达）。

## 4. 参数默认值建议（可直接批）

| 参数 | 建议默认 | 理由 |
|---|---|---|
| `limits.perProvider` | `{ default: 2, agnes: 2, ofox: 4 }` | 保守起步；按实测定 |
| 单项超时 | `180 s` | 实测单张 8–14 s，180 s 足够容纳重试与长尾 |
| 异步阈值 | `> 8 项` 转异步 run | 小批量保持同步体验 |
| 成本确认阈值 | `items × n > 30` 需 `confirm: true` | 一次调用最大 20×4 = 80 张，30 是保守线 |
| 厂商熔断 | 429 后对该厂商静默 `5 s` | 配合 `Retry-After` 使用 |

## 5. 我没有验证的（implement 前要先查/先测）

1. **DSH 运行时是否真的会并行调用**我们的工具（我们声明了 `isConcurrencySafe: true`，
   但"声明允许"≠"实际会并"）。**这决定 R1 的严重程度**：若不并行，R1 的紧急度下降一档；
   但**声明出去的契约就是承诺**，仍应按"会并发"来加固。
2. `maxBatchItems: 20` 是否在**工具入参校验**里硬挡（我只看到配置项），以及挡的报错文案。
3. run 记录里**是否已存"每项所属的 module/尺寸"**（§41 看到 `project.json` 有 module+size；
   `run-store` 的 `RunItem` 结构需再核），这决定 `resume` 能否精确只补未成功项。
4. 作品库侧现在**有没有**"进度/取消"入口（`POST /runs/<id>/cancel` 存在，但 UI 是否用上未确认）。
